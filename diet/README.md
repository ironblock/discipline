# `diet`

`diet` is a Rust project which represents the dogma and the core mechanical aspects of the overall program. 

It's primarily a library, but exists primarily to apply a `regimen` - a fixed combination of variables expected to describe the character, performance, and timing of a session (live or replayed).

**A regimen** is a TOML file naming the arm, the dogma version, the substrate (a served model on a registered machine, `substrates/README.md`) and the sampler a session runs under, and what else it is held to (`diet check-regimen` reads one). Three ship as specimens:

- [`drive/floor.toml`](drive/floor.toml) binds a session to the maintainer's floor, the 3.8 line's config r2 on TabbyAPI (#497). It starts only against a server reporting what that substrate's entry declares.
- [`drive/dev-loop.toml`](drive/dev-loop.toml) names the canned substrate: a scripted server inside this crate, with no weights. It is served only by that canned server, which the batch drive starts for itself.
- [`drive/replay.toml`](drive/replay.toml) is a rehearsal: commands, approvals and a record, with no model. Its substrate, `canned-replay-tools`, is served by `diet-drive replay`, which answers each ask with a captured llama.cpp `bash` call and then that session's answer, so the shell gate and its approval prompt run.

**Tool output is capped as it arrives** (#554): what the model is shown of a command's output stops at 2000 lines or 50 KiB, the convention of the harnesses it is compared with. Past the cap it sees the head and the tail with a notice, and the whole output is kept in the recording's `files/` by digest, for it to read in slices. A regimen's `[tool_output]` sets `max_lines` and `max_bytes`, or `cap = false` to keep every output whole. `session.start` and the record's start name the state the session ran under.

**A meditation can keep a recent tail** (#552): a regimen's `meditation_tail_tokens = N` keeps the old trunk's most recent whole turns, within N estimated tokens (characters ÷ 4), after the refill, as they sat on the trunk. A tail starts only at a user message, and the turn that would cross N is not kept. 0, the default, is the total refill. The meditation line and the record's meditation row name the depth and what was kept. A tail that kept no turn, because the newest alone is over N, puts that turn's estimated tokens on the meditation line as `newest_turn_tokens` (#693). The surface uses it to warn the operator.

**A meditation fires before the window fills** (#617): before every trunk request, the turn's own steps included, a served session that keeps working memory and knows its window refills the trunk when the prompt as sized (#588) would leave less than max(20,000, the output cap) tokens of the window: OpenCode 2's reserve, where Pi and OpenCode both compact automatically and Qwen Code's larger reserve breaks the tie on the number. Under a turn, the running turn is split (#813), as OpenCode 2 and Pi split it: its ask rides after the refill, then only its most recent whole steps within a budget, the last step always. A step is an assistant message and what follows it, so a call is never parted from its result. The compaction persists (#886): the steps it compacted do not come back when the turn settles, so the trunk after it holds the refill, the turn's ask, and the steps it kept and ran. A log says so with `compaction_persists` on its `session.start`; an earlier log's compacted steps rejoined the trunk at the settle, and its record is projected as they did. The steps before them are compacted with the turns before the turn: archived, their outputs carried by `meditation_tool_outputs`, and what they did already in working memory through in-turn capture. The budget is OpenCode 2's: a quarter of the window less the reserve, between 2,000 and 15,000 tokens (15,000 on the floor). Pi keeps a flat 20,000 and Qwen Code keeps no tail, so the tie goes to the smaller. The meditation line names the steps kept and compacted (`turn_steps_kept`, `turn_steps_compacted`). With nothing in working memory, or no earlier turn and no step the refill would drop, the request goes as it is, as all three harnesses send it. A request that overflows anyway (#616) is meditated once more and sent again, once per turn, as each of the three compacts and retries once after an overflow. A regimen turns it off with `meditation_window = "off"`. The meditation line and the record's meditation row carry reason `window`, the prompt that fired it and the window.

**An image is estimated by its pixels** (#588's estimate, extended). A message's text is estimated at four characters a token. An image part is estimated at one token per 32×32 patch of its pixels: the registered vision lines cut 16-pixel patches and merge them 2×2. Its width and height are read from its header when it is attached (PNG, JPEG, GIF). It never costs fewer than 1,024 tokens, the floor's minimum. An image whose header is not read is taken at 16,384, the most the Flash-Next line takes. Its encoded bytes are never counted: a 3.4 MB screenshot is about 7,000 tokens, not 1.1 million. The served usage after the request corrects the estimate, as it does for text. Every decision the estimate feeds goes through it: the window trigger, the render fit, fork admission and the pool count. A trunk waits on the forks in flight only when they are why it does not fit, never for room an empty pool would not give it either.

**A fork is sized against its own server's window** (#406). Its tail is a regimen's `fork_tail_tokens`, or 8,192 (#826) or the output cap if that is less, clamped as the trunk's is (#588). 8,192 is sized for what an interview answers: across three agent-driven T1 runs, 511 fork answers used at most 7,627 tokens. Forks that settle `truncated` are counted on the record, so the default can be checked. Its prompt is sized from the trunk's measurement when it shares the trunk's prefix on the trunk's server, and from its own estimate otherwise. A fork whose window would leave less than the clamp's floor is never sent: its `fork.settled` is `refused`, with `refused: "pool"`. A fork sent to the trunk's own server with a prompt that is not the trunk's prefix (a `last:N` view) names `hazard: "may-displace-trunk-cache"` on its fork line, because on a shared pool its pages can push the trunk's cached prefix out. It is logged, not refused. The start row's `fork_memory_share` lever names the tail. The registry's `under_pressure` says what each engine does when its pool runs out, read from source and unconfirmed.

**A fork runs nothing it calls** (#806). A fork cut from the trunk carries the trunk's tools, so its answer may be a call. Every call is logged as a `tool_call` on either capture route. A record tool's call (`update_record`, `resolve_entry`) is folded as the fork's patches, through the same groundedness gate as the trunk's. On the `fields` route the prose beside it is read too, and the fork settles `value` if either wrote. Any other call, the phase tool included, runs nothing and is counted on the fork's `fork.settled` as `not_run`. A fork with only such calls and no answer settles `unparseable`.

**A meditation can audit working memory and warm its refill** (#504), each off by default and named on the start row. With `meditation_audit = "on"`, an operator, phase or cadence meditation first puts the dogma's pinned audit ask (`AUDIT_Q_HUMAN`, `AUDIT_Q`, `AUDIT_Q_CADENCE`) over the working notes, numbered 1..n. It is a side call off the warm trunk on the `audit` lane, logged as a fork. The answer is read by the `audit` format, one line per note: `KEEP` leaves the note, `UPDATE: <note>` supersedes it, and `REMOVE — <reason>` (or `— dup of #k`) retires it. The result folds into working memory before the refill. An answer outside the grammar folds nothing, is logged `unparseable`, and the meditation goes on. With `meditation_warm = "on"`, the refilled trunk is sent once with an output cap of one, so the next ask finds it cached, and the meditation line carries the warm's timings. An ask meanwhile cancels the warm, and a `window` meditation is never warmed. The system prompt is untouched throughout: the audit is asked after the trunk, and the refill sits after the head. An audit over more notes than fit is fitted (#821) to the window less the clamp's margin and the output cap, so its answer keeps the whole cap. The prompt is sized as its request will be, from the trunk's measure. The notes the operator flagged or edited are audited first, since they are the operator's explicit ask; then the newest that fit. An audit over many notes is split into chunks of `meditation_audit_chunk_notes` notes, 100 unless declared. Each chunk is its own audit fork, its line naming its `chunk` from 1, the operator's changed notes in the first and then the newest. Each chunk folds as one audit does. The chunks run one after another unless `meditation_audit_concurrency` says how many may be in flight at once (1 unless declared). No more overlap than the trunk's server batches (its entry's `served_max_batch_size`) or its pool holds, each counted as the engine holds it; the first always goes. On the record tools' route they run one at a time whatever is declared, since a chunk's patches there may supersede another chunk's note. Their calls' lines are logged as they come, interleaved, but each chunk is folded, settled and its patches logged in chunk order, once every chunk before it has been: working memory is what one after another leaves, in content, order and structure, its ids citing the run's own fork seqs. One stop reaches every chunk in flight. A chunk's call runs from its `fork` line to its answer's line (or its stop's or failure's); its `fork.settled` is logged when it folds, so one that answered before an earlier chunk settles after it. The audit runs from the first `fork` to the last `fork.settled`. The default comes from the T1 runs' audits: under xhigh reasoning, 69 and 95 notes fit a 32,768 cap, while 231 to 517 spent the whole cap reasoning. A chunk cut off by its cap folds nothing, and the meditation line names how many notes its chunks never reached (`audit_notes_unreached`). The start row's `meditation_audit_chunk` names the chunk size, and `meditation_audit_concurrency` the declared count (`:default` when undeclared) and the effective one, with what lowered it: `4:effective:2:served_max_batch_size`, `4:effective:1:tools_route`.

**The operator's edits and flags are reconciled at the next meditation** (#150). `edit-entry` and `flag-entry` change a live note, and the model's lanes cannot rewrite what the operator wrote. Each pending change is marked on its note, ` [edited by the operator]` or ` [flagged: <note>]`, in the next meditation's refill and, with `meditation_audit = "on"`, in its audit, which is then the trigger's reconciling ask (`AUDIT_Q_HUMAN_RECONCILE`, `AUDIT_Q_RECONCILE`, `AUDIT_Q_CADENCE_RECONCILE`) asking the model to address each. An audit answer that parses addresses every marked note. The meditation line records `operator_changes` and the `unaddressed` ones, which stay pending, marked again, at the meditation after.

**The reconcile gate** (#150): `reconcile_gate` decides whether a meditation refills over an operator change no audit addressed, and the start row names it.
- `carry`, the default, refills and records the change `unaddressed`, carried to the next meditation.
- `refuse`, which needs `meditation_audit` on and the fields route:
  - The meditation puts the same reconciling ask once more, over only the notes whose changes are left.
  - If any change is still left, the meditation is held and logs `meditation.held` naming those entries. An ask is refused `meditation-held`.
  - The operator edits and declares the meditation again, or posts `{"kind":"refill-anyway"}`. That refills, carrying them unaddressed, and marks the meditation line `refilled_anyway`. With no meditation held it is refused `nothing-held`.

**Phase moves take two keys** (#124, #788): the model or the operator proposes, and the other accepts.

- **The phase tool:** whenever phases are declared, `propose_phase_transition` is offered, self-capture or not, described by the pinned `PHASE_TOOL` (dogma v11).
  - Arguments: `to`, `reason`, and `accept` (a boolean) when answering the operator.
  - A move outside the phase's suggested and allowed transitions is refused in the graph's word, and the model is shown that word.
- **The model proposes.** An allowed proposal is the session's one pending proposal.
  - It ends the model's turn: the model is shown the pinned `PHASE_PROPOSED`, and the turn settles `final` after the call.
  - A `phase.proposed` line records it with its evidence: the phase's `phase_steps` and `phase_tokens`, the `tokens_since_meditation`, and whether the operator `meditated_by_hand` with no turn since.
  - Rule on it with `{"kind":"ratify-phase","call":"<the call's id>","choice":"meditation"|"keep"|"stay"}`: `meditation` declares the meditation that moves to the proposed phase; `keep` moves the phase and keeps the trunk (v7's `continue` is read as `keep`); `stay` declines.
- **The operator proposes** with `{"kind":"propose-phase","to":"<phase>","meditate":true|false}`. `meditate` defaults to true, meditate-and-move being the suggested option.
  - A `phase.proposed` line records it with the same evidence and its `meditate`.
  - The model is asked in a note on its next ask, the pinned `PHASE_OPERATOR_PROPOSAL`, logged as a `notice`. It answers through the tool with `accept`.
  - A `phase.answered` line records the answer. If the model accepts, a `phase.ruled` line says `by: model` and the move follows the operator's choice: kept at once, or through a meditation once the turn has ended (with nothing to refill from, kept).
  - Refused `proposal-pending` while the model's own proposal waits.
- **The operator moves alone** with `{"kind":"move-phase","to":"<phase>","meditate":true|false}`, unless the regimen sets `operator_unilateral = false` (true by default), when it is refused `not-unilateral`; the start row's `operator_unilateral` lever says `on` or `off`. A `phase.ruled` line with no `call` says `by: operator`.
- **The starting phase:** `{"kind":"start-phase","phase":"<phase>"}` chooses it before the first ask, logged `phase.started`; it is refused `already-asked` after.

A `phase.ruled` line records every ruling and move.

**A meditation can carry the tool outputs it compacts away** (#553): a regimen's `meditation_tool_outputs` says what the refill carries of the outputs in the turns before the kept tail, in a section after the rendered working memory, one entry per call in call order. `evict`, the default, carries nothing. `keep` carries each output as the trunk had it, after the cap. `reference` carries a line naming the tool, its arguments, and the output's size and sha256, with the whole saved by digest in the recording's `files/`. `salient` carries the verbatim excerpts the read fork quoted from each output. The kept tail's outputs are untouched. The meditation line names the state, logs the section as sent with how many outputs and bytes it carried, and the start row names the state beside the cap.

**The tool surface** (#557): a regimen's `tool_surface = "standard"` offers `read`, `write`, `edit`, `grep` and `glob` beside `bash`, shaped as the compared harnesses shape them. `bash` alone is the default. Every tool runs through the session's confinement, as `bash` does, and no approval gate decides them; each call is logged under its tool's name.

**The interview cadence** (#564): a regimen's `interview_cadence` says when the capture gap's forks fire, and on what. `gap`, the default, fires at most one: the judgment ask on an operator-marked turn, else the class ask on the turn's last read. `per_class` forks on every call the router routes to a class ask. `per_call` forks on every call that ran, with the generic ask for a call the router would not interrupt. `turn_boundary` asks the judgment question at every turn's end. Every state queues its forks into the gap in call order, one after another. `interview_threshold_bytes = N`, unset by default, forks a read only when its output is at least N bytes. Each fork line names its `trigger`, and the start row names the cadence. `interview_skip_self_recorded = true` (off by default, #611) skips a fork the turn's own self-capture already recorded: an `update_record` the turn made, recorded under a field the fork's ask asks for, and for a call's fork made after that call. A `fork.skipped` line names the fork and the capture call that recorded it.

**Mechanical capture** (#784): a regimen's `mechanical_capture = "on"` (off by default) patches each settled tool call's touches into working memory as the call settles, with no model call and no fork. The mechanical lane reads the call as the shell would: each file read, written or edited becomes one entry per path, `files: <path>` (id `mechanical/<path>`, the path relative to the worktree), a later touch appending its provenance (lane `mechanical`, the turn, the step), and a delete retiring it; an `ls` adds `files: listed <dir>`. A file deleted and then touched again is a fresh entry, `mechanical/<path>#2`. The operator's entries are theirs, as to any writer. The lever opens working memory by itself, with no warrant or self-capture: a refill holding only `files:` entries beats a session dead of its window, since the model can re-read what they list and archive recall covers the rest. Each change is a `patch` line with lane `mechanical`, and the start row names the lever.

**The refutation interview** (`refutation_interview`, off by default; ruled 2026-10-16, #878). A corrected belief stays in working memory as what was believed. With `refutation_interview = "on"`, a step whose call failed, as `trouble` reads one (a `bash` command that exited non-zero, timed out, or showed error-shaped output; a standard tool that reported its own failure, never content its result quotes, #894) warrants a fork in the turn's gap. The operator's message warrants one as it arrives (#904): cut from the trunk and the message, with its notes, before the turn reads it, so its prefix holds what the model believed and what contradicts it, never a step of the turn. The turn's first trunk request waits for it -- measured on the lever's paired runs at a median 3.9 s (p90 18.6 s) -- so any refutation it writes is in working memory before the turn's first step, and its prefix is the trunk's own next prompt, warming the trunk's cache. Its line says `timing: "arrival"`, its `at` the `ask` (log v10); a stop during it ends the turn, cancelled. Each source is cooled on its own, once `refutation_failed_cooldown_steps` or `refutation_operator_cooldown_steps` steps (3 unless declared) have passed since that source's last fork, the turn's answer counted as a step; the two never compete, the gap taking only a failure's. Failed commands are cooled too: `trouble` fires on every error, and it was T1's measured overcollector. A background job's start is no failed command: its output lists the statuses it may end in. The fork asks the pinned `REFUTE_Q` (dogma 12): what the trigger shows, the live notes most like it by id -- the `refutation_candidates` (8 unless declared) nearest the trigger's text by `note_dedupe`'s TF-IDF cosine, so an interview's cost is at most that many notes -- and whether it shows something the model believed was wrong. It is answered through one tool, whatever `capture_modality` says: `refute_beliefs` (pinned as `refutation/tool`, dogma 12), called once with `refuted`, a list of every belief shown wrong. Each item names exactly one of `note_id` (any live note, listed or not) and `claim` (quoted, never written down), and says `confidence` (an integer from 1, absolute uncertainty, to 10, complete conviction, as held then), `because` and `now`. Each item is checked on its own: one that names a note voids it with the claim believed `now`, of the note's kind, carrying its confidence, why it is wrong, and a pointer the harness writes from the trigger itself (`call <id>` for the failed command, `log seq <n>` for the operator's ask). A claim never written down is added as a `fact`, quoted, and superseded at once. Item `i` is entry `r<request>/<call>.<i>`. An item outside those bounds -- a confidence of 0 or 11, both a note and a claim or neither, a note not live -- is refused and named on the call's `capture` line, and the good items beside it still write. Every call in the answer is read. `[]` says nothing was shown wrong: the fork settles `decline`. A fork that made no call, prose only, settles `unparseable`; its prose is never read. The tool is declared from the first request, so a refutation fork's request carries the trunk's tools and its prefix, and the trunk may call it too: its refutations are written as a fork's are, on the `trunk` lane, pointing at the step's request (`log seq <n>`), since the model had seen the evidence by then. The cost of the harness's pointer: a refutation that rests on a read rather than the trigger still points at the trigger. The superseded note stays in every refill as `was: <claim> (held at <n>/10), wrong because <why> [<pointer>]`, kept whole as the brief is, and the audit is never shown its correction, so it cannot prune the correction as a duplicate of the claim. A supersede's `patch` line carries the refutation as `refuted` (log v9, its `confidence` an integer from 1 to 10), the fork line names the notes offered (`offered`, the prompt's list and no gate), and the start row names the lever (`on:failed-cooldown-3-steps:default:operator-cooldown-3-steps:default:candidates-8:default`). A cooldown or a count that is not a whole number above 0, or one set with the lever off, is refused at start.

**Write-time dedupe of similar notes** (`note_dedupe`, off by default; approved 2026-10-15). With `note_dedupe = "on"`, a new note whose text is at TF-IDF cosine `note_dedupe_threshold` or above (0.40 unless declared) to a live note of its own kind is merged into it, as an identical note already is: its id becomes an alias of that note, which gains its provenance. Its `patch` line carries `merged`, the note that absorbed it, and their `cosine`, and the start row names the lever (`tfidf:0.40:default`). The cosine is the T1 duplicates study's: lowercased tokens (a word character, then word characters, `.`, `-` or `/`; or a lone word character), sublinear term frequency, smoothed IDF, the kind's tag not scored. The study fitted IDF on every note of a finished session. Here only the notes live so far exist, so IDF is fitted on the kind's live notes and the new one, afresh at each write; the study's precision 0.947 and recall 0.667 at 0.40 are for its offline form, not this one. The evidence is gotcha notes only: two thirds of a T1 run's gotchas duplicated an earlier one, almost all restatements. The lever applies to every kind, each against its own. A note has a kind when its text opens with the kind's tag and `: `, as the lines route writes every note; the record tools' route writes the field apart from the text, so its notes are deduped by exact text only. A malformed threshold, or one set with the lever off, is refused at start. The code is [`src/dedupe.rs`](src/dedupe.rs).
**Interviews during the turn** (#782): `interview_timing = "during_turn"` (`gap` by default) runs a step's forks while the trunk goes on, instead of in the gap after the turn settles.
- **The cut:** a fork a step warrants (the `read` warrant at `per_class` or `per_call`) is cut from the trunk as it stood after that step's tool results. It is sent at once, beside the trunk's next request, in a spare slot.
  - It sees the whole trunk at the cut, its warm prefix, whatever `fork_view` says; its line names the view it overrode (`view_overridden`).
  - The scoping judgment at the turn's end still runs in the gap.
- **Slots:** at most the trunk's server's `serving_slots` less one run at once, or an offboard seat's own count; the rest queue in step order. One still queued when the turn settles runs after it.
- **The queue is bounded** (#822): at most `fork_backlog` forks wait for a slot, 3 unless the regimen says. That is one step's trouble trio, so the newest step's full set is never cut short, and on a two-slot server the queue drains in three fork calls after the turn. Past the bound the oldest queued are dropped, never one in flight, and each drop is a `fork.skipped` line with `reason: "backlog"` and the `cut` it was cut at. A fork run long after its step asks about a trunk that has moved on. The start row's `fork_backlog` lever names the bound.
- **A declared meditation waits only for the forks in flight** (#822): while only forks cut during the turn hold the session in `capture`, `declare-meditation` is admitted rather than refused `in-flight`. The queued forks are dropped as `backlog`, and the meditation runs once those in flight settle and the turn is over.
- **Folding:** a fork's patches fold into working memory as it settles, mid-turn. Nothing enters the trunk mid-turn.
- **Ending:** the session's `end` cancels forks in flight; the turn's `cancel` lets them finish. The session awaits only once the last has settled.
- **The pool:** serve never puts more on the trunk's server than its window holds (#826), and it counts each job the way the engine holds it. TabbyAPI admits a round when its prompt and output so far, aligned up to the 2,048-token recurrent checkpoint interval, fits the cache, and ExLlamaV3 reserves that plus its draft tokens in 256-token pages (Track 6, #839). So each job is counted as its prompt plus its output cap, rounded up to whole chunks, plus two chunks more. One job alone then fits exactly when it is at most the pool less two chunks: 159,744 on the floor. The chunk is the entry's `served_chunk_size`, else 2,048. On the floor a job past the pool by one page does not just fail: the engine's generator fails, and every job on the server is cancelled, the trunk's with it.
  - **A fork** is sent with the output cap left in whole chunks, up to its tail. One that would leave less than the clamp's floor waits at the queue's head until a fork settles or the turn ends. A fork that could not fit even in an empty pool is refused unsent, and its `fork.settled` carries the four numbers (`window`, `trunk_tokens`, `beside_tokens`, `fork_tokens`), the trunk's and the forks' as the engine holds them.
  - **A trunk request** sized while forks are in flight is checked at send time, its prompt as it is now, so tool results that grew it past its last request are counted. Its cap is cut to what the forks leave, logged as `trunk.clamped` with the cap the window alone gives it, the cap it is sent with, and the forks. If even its prompt and the clamp's floor do not fit, it waits for them to settle, and no queued fork is sent meanwhile. That is logged as `trunk.waited`, with the forks, how long it waited, and the caps.
- **A shared prefix:** on a server whose registry entry declares `served_prefix_shared = "true"`, measured to share a prefix's pages between concurrent requests, a fork cut from the trunk reserves only its tokens beyond the prefix the trunk holds (#797). Without the declaration every prompt counts in full. Each cut fork's line names its reservation (`reserved`) and whether its prefix was counted as shared (`prefix_shared`); a refusal's `fork_tokens` is that reservation.
- **The log:** a fork's line names the step's `tool_call` it was `cut` at and `timing: during_turn`, and each trunk request names how many forks were in flight `beside` it.
- **Refused at start:** serve refuses the timing when nothing warrants a fork at a step (a call's warrant, or a step warrant below), or when the registry declares fewer than 2 `serving_slots` for the trunk's server (or none for a seat). The start row's cadence names `during-turn`.

**Warrants by what a step produced** (#783): `interview_warrant` may also name `evidence`, `trouble` and `open`. Each is gated on every trunk step, the final answer included. The gates, their numbers and their order are the predecessor's, its intent (`diet/src/drive/warrants.rs`).
- **`evidence`:** a call to `read` or `bash` whose shown result is at least `evidence_min_chars` (3000) characters. The first `evidence_per_step` (2) in call order each fire the pinned EVIDENCE ask, filled with the call (`bash of <command>`) and its size. A directory listing never forks, and an output a fork already covered this turn forks no second time.
- **`trouble`:** a call that ran and exited non-zero or timed out, or a standard tool that reported its own failure, or a `bash` call whose shown output matches the predecessor's error pattern. A standard tool's result quotes content, so its text is never read for an error (#894). Or: the step's reasoning and text matching its surprise pattern, at most once every `trouble_cooldown_steps` (3) steps. An error always fires. It fires three forks, the pinned GOTCHAS, DECISIONS and CONSTRAINTS asks.
- **`open`:** every `open_every_steps` (10) steps, counted across the session, it fires the pinned OPEN_NEXT ask.

**The step warrants' gate** (`warrant_gate`, approved for testing 2026-10-14). By default it is `regex`, #783's patterns, unchanged. With `warrant_gate = "classifier"`, a step's `trouble` and `open` forks fire on scores from a Sidekick classifier (`POST /v1/classify`, `format = "nli"`). The classifier only gates: it never writes into working memory.
- **No product defaults.** `[warrant_classifier]` names all of these, or serve refuses to start:
  - the endpoint;
  - the model and its revision;
  - the compute units;
  - the truncation side;
  - the timeout;
  - the windowing (`prose_window_sentences`, `prose_window_chars`, `output_tail_chars`);
  - `windowing`: the issue whose windowing rule the thresholds were fit on (#902), `899` for this build. A regimen naming another is refused, the refusal naming both: thresholds fit on other windows need a refit, as #900 refit #899's. The start row's `warrant_gate` word carries it (`classifier:<model>@<revision>:windowing-899`);
  - the windows one request carries (`batch`, the model's `max_batch`).
- **Probes.** Each `[warrant_classifier.<name>]` table is a probe. It names:
  - its `class` (`gotcha`, `decision`, `constraint` or `open`);
  - its `input`: `prose`, `output`, `both`, `previous_prose` or `previous_output`, the last being the output a step's prose answers;
  - its `hypotheses`, sent whole as candidate labels with the template `{}`;
  - its `aggregate` (`max` or `mean`);
  - its `threshold`.
- **Scoring.** Each hypothesis scores the max over the probe's windows, scored independently (`multi_label`). The probe's score is the max or mean over its hypotheses. Its class fires at or above the threshold.
- **What fires.** A trouble fork asks only the trio classes that fired, with no cooldown. `open` fires on its class when a probe gates it; otherwise it fires on its cadence. `evidence` is unchanged.
- **Windows.** They are the trouble-detector register's, but for one rule:
  - prose split into sentences after `.`, `!` or `?`, never after a colon (#899), and packed into windows of at most 3 sentences and 400 characters;
  - each call's output as `$ <arguments>` and its last 800 characters, plus the first error-looking line.
- **Holding the session.** The classifier is called with the session's lock released. A stop meanwhile drops the decision as `stale`.
- **Logging.** Every probe's decision is a `warrant.gated` line: the step's trunk request, the class, score and threshold, whether it fired, the model, revision and compute units, and the latency.
- **Fallback.** A classifier that is unreachable, errors, times out or serves another model, revision or compute units than declared drops that step back to the patterns. The fallback is logged with its reason, and the turn never fails.
- **Replay.** A recorded run's decisions replay from its log, keyed by the step's trunk request, without the classifier.
- **No convention to follow.** No harness this one follows gates its side calls with a classifier.


A step fires its evidence forks, then the trio, then open. They run in the gap, or, under `interview_timing = "during_turn"`, cut at the step; a final answer's always run in the gap. Each fork names its warrant (`why`), its pinned ask (`ask`) and the step or call that fired it (`trigger`: `evidence:<call>`, `trouble:<request>`, `open:<request>`). The start row's `fork_warrant` names each step warrant with its numbers.

**Background commands** (#614): `bash` takes `is_background: true`, and the call returns at once with a job id, an output file and a status file, while the command keeps running under the session's confinement. `task_stop` stops a job's process group. When a job ends, its output is kept by digest, a `background.ended` line logs it, and Qwen Code's `<task-notification>` follows the next ask. The operator can move a running call to the background with `POST /commands {"kind":"background"}`, which answers with the job id or is refused `nothing-running`. A turn's cancel leaves jobs running, and the session's end kills them. The shape is Qwen Code's, the only compared harness whose shell has it. `background_commands = false` turns it off, and the start row names it.

**A command times out** (#613): a `bash` call ends at its timeout, 120000 ms unless the regimen's `bash_timeout_ms` says otherwise (0 for none), or the call's own `timeout` (milliseconds, up to 600000). The timeout is the vote's: OpenCode 2 and Qwen Code agree, and Pi has no default. At the timeout the call's process group gets `TERM`, then `KILL` 200 ms later, and the call is answered with Qwen Code's words and what it printed; the turn goes on. Fifteen seconds before, a `timeout.near` line tells the surface, never the model, so the operator can move the call to the background, where it has no timeout. `session.start` names the default, and the start row names it as `bash_timeout`.

**Two binaries**, built from the repository root with `cargo build -p discipline-diet`:

- `diet` is the command-line reader of every format (`diet check-log`, `diet check-record`, ...). Anything outside this library that reads a format goes through it.
- `diet-drive` drives a session. `diet-drive <regimen> <worktree> <output.jsonl>` runs a pinned three-turn script as a batch. `diet-drive serve` serves one interactive session over HTTP, which is what a harness talks to. `diet-drive --help` and `diet-drive serve --help` print each form's usage.
